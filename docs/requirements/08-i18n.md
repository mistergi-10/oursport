# Slice 8: Multi-language support (i18n)

## Summary

Add runtime multi-language support (German, English, French) to the Expo app, with auto-detected locale on first launch (German fallback), persisted manual override, locale-aware date/time formatting, and stable machine-readable error codes from the API so the client never displays raw English server strings inside a localized UI.

## Current state (verified in code)

- Every user-facing string in the app is a hardcoded German literal. There is no `i18n`/`i18next`/`expo-localization` dependency anywhere in [oursport/package.json](../../oursport/package.json), and no partial i18n scaffolding exists in the repo (confirmed via workspace-wide search for `i18n`/`i18next`/`expo-localization`).
- The hardcoded copy is spread across **all 14 screens** under [oursport/screens/](../../oursport/screens/) (`WelcomeScreen`, `LoginScreen`, `SignupScreen`, `ForgotPasswordScreen`, `ResetPasswordScreen`, `MainTabs`, `Matching`, `MatchesList`, `ConversationScreen`, `Events`, `CreateEventScreen`, `EventDetailScreen`, `ProfileScreen`, `PrivacyScreen`, `ReportScreen`) plus 2 of the 10 shared components ([oursport/components/Header.tsx](../../oursport/components/Header.tsx)'s default `actionAccessibilityLabel="Filter"`, [oursport/components/SocialAuthButtons.tsx](../../oursport/components/SocialAuthButtons.tsx)'s button labels and `Alert.alert` copy) plus 3 `lib/` modules: [oursport/lib/constants.ts](../../oursport/lib/constants.ts) (`tabLabels`, the 31-entry `sports` list, the 3-entry `levels` list), [oursport/lib/format.ts](../../oursport/lib/format.ts) (`formatRelativeTime`'s `"Jetzt"`/`"vor X Min."`/`"Std."`/`"Tg."`, `formatEventMonth`'s hardcoded German month abbreviations, `eventJoinLabel`'s button copy), and [oursport/lib/api.ts](../../oursport/lib/api.ts) (`describeApiError`'s generic 429 fallback). A rough, verified count across these files: **373+ matches** for capitalized German word/phrase literals (grep across `oursport/screens` and `oursport/components`, excluding pure syntax/keyword false-positives). This confirms the "every screen, pervasive, mechanical" framing — there is no small corner of the client to localize, it is the whole app.
- `oursport/App.tsx` itself holds no UI copy (per slice 6's decision, it was reduced to composition/navigation wiring) — nothing to change there.
- `sports` and `levels` ([oursport/lib/constants.ts](../../oursport/lib/constants.ts)) are German words used as **both** the UI display label **and** the literal value stored in `profiles.sport`/`profiles.level` and sent to the API (e.g. `SignupScreen` defaults `sport: "Laufen"`, [oursport/screens/SignupScreen.tsx](../../oursport/screens/SignupScreen.tsx#L24)-[L25](../../oursport/screens/SignupScreen.tsx#L25)) — these same strings are used for exact-match filtering server-side (`eq(profiles.sport, ...)`, discover/events `OR` inclusion rule). Translating the *display* of these values without touching the *stored/wire* value is a load-bearing design constraint for this slice (see Decisions).
- `ReportScreen`'s `ReportReason` values (`"spam"`, `"harassment"`, `"fake_profile"`, `"inappropriate_content"`, `"other"`, [oursport/screens/ReportScreen.tsx](../../oursport/screens/ReportScreen.tsx#L28)-[L32](../../oursport/screens/ReportScreen.tsx#L32)) are already locale-independent technical identifiers — only their German display `label`s need translation, the enum values sent to the API are unaffected.
- `oursport/lib/format.ts`'s `formatMessageTime` hardcodes `toLocaleTimeString("de-CH", ...)` ([oursport/lib/format.ts](../../oursport/lib/format.ts#L16)-[L18](../../oursport/lib/format.ts#L18)); `formatEventMonth` hardcodes a 12-entry German month-abbreviation array ([oursport/lib/format.ts](../../oursport/lib/format.ts#L20)); neither takes a locale parameter today.
- **Server-side strings are already in English, not German**, and they leak into the otherwise-German UI verbatim in several flows. `server/src/index.ts` returns `{ error: "<English message>" }` on ~40 call sites (e.g. `"Email is already registered"`, `"Invalid email or password"`, `"Profile not found"`, `"Event is full"`, confirmed by grep). The client's `ApiError`/`authRequest` ([oursport/lib/api.ts](../../oursport/lib/api.ts#L13)-[L17](../../oursport/lib/api.ts#L17), [L48](../../oursport/lib/api.ts#L48)-[L58](../../oursport/lib/api.ts#L58)) carries that string as `Error.message`, and several screens render it **verbatim** via the `caught instanceof Error ? caught.message : <German fallback>` pattern — confirmed in `LoginScreen` ([oursport/screens/LoginScreen.tsx](../../oursport/screens/LoginScreen.tsx#L38)), `SignupScreen` ([oursport/screens/SignupScreen.tsx](../../oursport/screens/SignupScreen.tsx#L50)), `ForgotPasswordScreen`, `ResetPasswordScreen`, `ConversationScreen` ([oursport/screens/ConversationScreen.tsx](../../oursport/screens/ConversationScreen.tsx#L259)), and `CreateEventScreen` ([oursport/screens/CreateEventScreen.tsx](../../oursport/screens/CreateEventScreen.tsx#L71)). Concretely: today a German-reading user who enters a wrong password sees the English string "Invalid email or password", not a German sentence. This is a pre-existing bug that becomes impossible to ignore once the client is otherwise fully localized, and must be fixed as part of this slice (see Decisions) — it is in scope for "wherever the server returns user-facing strings", per the roadmap item.
- `oursport/app.json`'s `expo-image-picker` plugin config has one German OS-level permission-dialog string (`photosPermission`, [oursport/app.json](../../oursport/app.json#L26)) — this is baked into the native build and shown by the OS, not rendered by the app itself; it cannot be switched at runtime by the in-app language picker (see Out of scope).
- `server/src/email.ts`'s `sendPasswordResetEmail` is an unimplemented placeholder (dev mode just logs to console; production warns and no-ops, [server/src/email.ts](../../server/src/email.ts#L1)-[L13](../../server/src/email.ts#L13)) — there is no actual user-facing email template to localize yet.
- The app already has an established "persisted local setting" pattern this slice follows: dark/light theme in `AsyncStorage` under the key `"oursport-theme"` ([oursport/theme/ThemeProvider.tsx](../../oursport/theme/ThemeProvider.tsx#L7)), and the onboarding-seen flag under `"hasSeenOnboarding"` ([oursport/screens/WelcomeScreen.tsx](../../oursport/screens/WelcomeScreen.tsx#L22)) — both read once on mount and written on change, with no server round-trip. Locale preference follows the same shape.
- `oursport/package.json` confirms Expo SDK `~57.0.23`, React Native `0.86.3`, React `19.2.3` ([oursport/package.json](../../oursport/package.json)). `expo-localization` and `i18next`/`react-i18next` are current, actively-maintained packages with no Expo-57-specific incompatibility; `expo-localization` ships its own SDK-aligned version (installed via `npx expo install expo-localization` to get the `~57.x` build, consistent with how `expo-haptics`/`expo-image-picker`/`expo-location` are already pinned in this project). No existing dependency in the project conflicts with adding these.

## User stories

1. As a user opening the app for the first time, the app's language automatically matches my device/browser language if it's German, English, or French, and defaults to German otherwise.
2. As a user, I can change the app's language at any time (before or after signing in) from a visible, simple control, and my choice is remembered the next time I open the app.
3. As a user, every screen — authentication, matching, chats, events, profile, privacy, report — is fully in my selected language, with no stray text in a different language mixed in (including error messages).
4. As a user, dates, times, and relative timestamps ("2 min. ago" / "vor 2 Min." / "il y a 2 min") are displayed in a format and wording appropriate to my selected language.
5. As a user selecting my sport/fitness level, I see it in my language, even though the underlying value stored on my profile stays consistent for matching purposes.

## Data model changes

None. `server/src/db/schema.ts` is unchanged — no new table/column, no migration. Locale is a client-only, per-device preference (`AsyncStorage`), not a server-persisted profile field (see Decisions for why).

## API contract changes

- **Changed: every existing JSON error response** in `server/src/index.ts` (the ~40 `reply.code(...).send({ error: "..." })` call sites, plus the rate-limit `errorResponseBuilder` at [server/src/index.ts](../../server/src/index.ts#L237) and the generic Zod-validation/`500` handlers at [server/src/index.ts](../../server/src/index.ts#L1724)-[L1727](../../server/src/index.ts#L1727)) gains a stable, machine-readable `code` field alongside the existing `error` (English, human-readable, unchanged — still useful for logs/devs/non-localized debugging):
  ```json
  { "error": "Invalid email or password", "code": "invalid_credentials" }
  ```
  This is additive and backward-compatible (existing `error`-only consumers, if any external ones existed, keep working). Representative codes derived from the current message set: `email_taken`, `invalid_credentials`, `invalid_or_expired_code`, `profile_not_found`, `invalid_cursor`, `cannot_swipe_self`, `conversation_not_found`, `event_not_found`, `event_already_started`, `event_full`, `creator_cannot_leave`, `creator_already_attending`, `already_attending`, `cannot_block_self`, `cannot_report_self`, `user_not_found`, `invalid_password`, `rate_limited`, `validation_error`, `internal_error`. Each distinct existing English message maps to exactly one code (one-to-one, no two messages share a code); any message not explicitly listed above still needs a code assigned using the same naming convention when implemented.
- No endpoint, request shape, success-response shape, or auth rule changes. No locale negotiation (`Accept-Language`) is added to the API — see Decisions for why the server stays locale-unaware beyond this `code` field.

## Mobile UI/UX notes

### Library & file layout

- **Library choice: `i18next` + `react-i18next` + `expo-localization`** (installed via `npx expo install expo-localization` for the SDK-57-aligned version; `i18next`/`react-i18next` as plain npm deps). This is the de-facto standard combination for Expo/React Native i18n, has no known Expo-57/RN-0.86/React-19 incompatibility, and fits the project's existing "small, well-maintained dependencies added via `expo install` where applicable" pattern (mirrors how `expo-haptics`/`expo-location` were added in slice 7).
- Translation strings live as one JSON file per locale under `oursport/lib/i18n/locales/{de,en,fr}.json`, loaded as `i18next` resources at app start (`oursport/lib/i18n/index.ts` initializes and exports the singleton `i18next` instance plus a `supportedLocales = ["de", "en", "fr"] as const`). Keys are flat/dot-nested by screen or concern (e.g. `login.title`, `login.emailLabel`, `common.cancel`, `errors.invalid_credentials`, `errors.generic`), not split into multiple i18next namespaces — the app's total string count (~350-450 keys) doesn't warrant namespace-splitting overhead.
- A `sports` and a `levels` section in each locale file maps the **existing canonical German value** (used today as the wire/DB value, e.g. `"Laufen"`, `"Anfaenger"`) to that locale's display label, e.g. `"sports": { "Laufen": "Running", "Tennis": "Tennis", ... }`. German's own file maps each value to itself (identity mapping) — German is no longer an implicit default, it is one of three explicit, equally-maintained locale files. `oursport/lib/constants.ts`'s `sports`/`levels` arrays are unchanged (still the canonical list/order and the value submitted to the API); screens that render a sport/level now look up the translated label for display via this mapping instead of rendering the raw constant.
- `oursport/lib/format.ts` is a plain module (not a React component) and cannot use the `useTranslation()` hook; it imports the `i18next` singleton directly (`import i18n from "./i18n"`) and reads `i18n.language` as the default locale for its exported functions, each of which also accepts an optional explicit `locale` parameter (defaulting to `i18n.language`) so callers never have to thread it through manually. `formatMessageTime` switches from the hardcoded `"de-CH"` to a per-locale `Intl` locale tag (`"de-CH"` / `"en-US"` / `"fr-FR"`, see Decisions) with `hour12: false` explicit on all three (so English doesn't silently switch to 12-hour AM/PM while German/French stay 24-hour). `formatEventMonth` is rewritten to use `Intl.DateTimeFormat(localeTag, { month: "short" }).format(date)` instead of a hardcoded array, which is automatically correct for all three locales with zero per-locale maintenance. `formatRelativeTime`'s unit words move to `i18next` translation keys using its built-in CLDR pluralization (`_one`/`_other` suffixes — covers German/English/French plural rules), keeping the existing hand-rolled minute/hour/day threshold logic (no new `Intl.RelativeTimeFormat` dependency introduced; one locale mechanism per string is simpler than mixing two).
- `oursport/lib/api.ts`'s `describeApiError` and `authRequest` import the same `i18next` singleton and switch from raw `caught.message` / hardcoded German fallbacks to: (1) if the response carried a `code`, look up `errors.<code>` in the active locale, falling back to `errors.generic` if the code is unrecognized by the client (e.g. a code added server-side after this client shipped); (2) `authRequest`'s thrown `Error` also carries the parsed `code` (new field on a small `AuthError extends Error` class, mirroring `ApiError`) so callers can use the same lookup. **No screen ever renders `caught.message` (the raw English server string) directly to the user again** — every catch block in every screen is updated to go through this lookup instead of the `caught instanceof Error ? caught.message : fallback` pattern found in 6+ screens today.

### Locale selection & persistence

- On first launch (no stored locale preference yet), the app reads `Localization.getLocales()[0].languageCode` (via `expo-localization`) and sets the active `i18next` language to that code if it's one of `"de"`/`"en"`/`"fr"`, otherwise defaults to `"de"`.
- The chosen/detected locale is persisted to `AsyncStorage` under a new key `"oursport-locale"` (consistent with `"oursport-theme"`'s pattern) the moment it's first resolved (auto-detected or manually changed), and read back on every subsequent app start before auto-detection runs again — i.e. auto-detection only ever runs once per device/browser, exactly like `"hasSeenOnboarding"`.
- A manual language switcher is available in **two** places (so the choice isn't gated behind having an account yet):
  - A small, unobtrusive language control (e.g. a text button cycling "DE · EN · FR" or three small flag-free text chips) on `WelcomeScreen`, visible before sign-up/login.
  - A "Sprache" settings row in `ProfileScreen`, directly below the existing "Darstellung" dark-mode row ([oursport/screens/ProfileScreen.tsx](../../oursport/screens/ProfileScreen.tsx#L172)-[L180](../../oursport/screens/ProfileScreen.tsx#L172)), using three `Chip` components (reusing the existing `Chip` component already used for sport-filter/report-reason selection) labeled "Deutsch" / "English" / "Français" (each chip's own label is itself hardcoded in its own language, not translated, since it names a language — a standard i18n convention).
- Changing the language calls `i18next.changeLanguage(code)` and persists it; because every screen's copy is driven through `useTranslation()`, the UI updates immediately on the next render with no app restart required.

### Per-surface scope (this is the whole point of the slice — every surface is must-have)

- All 14 screens, the 2 components with their own literal copy (`Header`, `SocialAuthButtons`), and the 3 `lib/` modules (`constants.ts`, `format.ts`, `api.ts`) listed in "Current state" are translated — every hardcoded German (or English, server-error-leak) string the user can see is replaced with a `t("...")` call (or, for `format.ts`/`api.ts`, the singleton `i18n.t("...")` call) backed by a key present in all three locale JSON files.
- **Translation text quality**: French and English translations are produced for this slice (machine-translated/approximate is acceptable to unblock shipping — not a blocker per the roadmap brief) but are explicitly flagged as needing a follow-up native-speaker review pass before being considered final/polished copy; this does not block merging or shipping this slice. German text is carried over from the existing hardcoded strings essentially unchanged (it's already native-quality, written by the product owner).
- Pluralization/interpolation (e.g. "3 neue Profile in deiner Naehe", waitlist position "Platz N") uses `i18next`'s built-in `{{count}}`/`_one`/`_other` interpolation rather than manual string concatenation.

## Acceptance criteria

1. On a fresh install/first launch (no `"oursport-locale"` value in `AsyncStorage`), the app's language matches the device/browser locale when it is German, English, or French, and falls back to German for any other detected locale.
2. A manual language change (from either `WelcomeScreen` or `ProfileScreen`) immediately re-renders all currently-visible translated text in the new language with no app restart, and the choice persists across an app restart/reload.
3. No screen renders a hardcoded string in a language other than the currently active one — specifically, no screen renders `caught.message`/a raw server `error` string directly; every error path renders a translated string (either a specific `errors.<code>` translation or the generic `errors.generic` fallback).
4. Switching language changes the display label of every sport and fitness-level option without changing the value submitted to `POST /v1/profiles`, `PATCH /v1/me`, or any discover/event filter (verified: the wire value for a given sport/level selection is identical across all three active languages).
5. `formatMessageTime`, `formatEventMonth`, and `formatRelativeTime` render locale-appropriate output for each of the three supported locales (e.g. month abbreviations and relative-time wording differ visibly between `de`/`en`/`fr`), using 24-hour time in all three.
6. Every error response newly returned by `server/src/index.ts` includes a non-empty `code` field in addition to the existing `error` field, for every response that previously sent `{ error: "..." }` alone.
7. The three `Chip`-based language options in `ProfileScreen` and the `WelcomeScreen` language control both update the same persisted preference (changing it in one place is reflected in the other on next view).
8. `npm run web` (or `tsc --noEmit`) in `oursport/` and `npm run build` in `server/` both pass with no new TypeScript errors after this slice's changes.
9. No `server/src/db/schema.ts` table/column changes, and no new/changed endpoint request or success-response shape (only the additive `code` field on error responses) anywhere in this slice's diff.

## Out of scope

- Translating OS-level native permission-dialog strings (e.g. `oursport/app.json`'s `expo-image-picker` `photosPermission` string) — these are baked into the native build per the device's OS-level language via Expo's own per-locale config plugin mechanism, a separate system from this slice's runtime `i18next` setup, and are not addressed here.
- A server-side `Accept-Language`-aware or stored-per-user locale preference — the server stays fully stateless/locale-unaware beyond emitting the new stable `code` field; see Decisions for why translation is a client-only concern in this app.
- Localizing transactional email content — `sendPasswordResetEmail` ([server/src/email.ts](../../server/src/email.ts)) is an unimplemented placeholder with no real template to localize yet; this is deferred to whichever future slice actually wires up a transactional email provider.
- A professional/native-speaker translation review pass for the French and English copy — machine/approximate translation is accepted for this slice; a polish pass is a reasonable, non-blocking follow-up.
- Reordering the `sports`/`levels` selection lists per-locale (e.g. alphabetically in the active language) — the existing canonical order from `oursport/lib/constants.ts` is kept as-is in every locale.
- Right-to-left layout support — none of the three supported languages are RTL.
- Adding further languages beyond German/English/French.
- Localizing app store metadata (store listing title/description/screenshots) — out of scope for this in-app slice.
- Any App.tsx/navigation/schema change beyond what's needed to wire up the `i18next` provider at the app root.

## Decisions

Per this project's established convention (product owner pre-approves the maximal in-house-feasible option), the following are decided rather than left open:

1. **Library choice**: approved — `i18next` + `react-i18next` + `expo-localization` (SDK-57-aligned via `npx expo install expo-localization`).
2. **Translation storage format**: approved — one flat/dot-nested JSON file per locale under `oursport/lib/i18n/locales/{de,en,fr}.json`, single default `i18next` namespace, no per-screen namespace splitting.
3. **Sport/level canonical value vs. display label**: approved — `oursport/lib/constants.ts`'s existing German `sports`/`levels` arrays stay the canonical wire/DB values (zero backend/migration impact, zero risk to existing discover/event matching logic); each locale JSON file supplies a display-label lookup keyed by that same canonical string, including German mapping to itself.
4. **Date/time locale mapping**: approved — `de` → `"de-CH"`, `en` → `"en-US"`, `fr` → `"fr-FR"` `Intl` locale tags, with `hour12: false` forced on all three so time format stays consistently 24-hour across languages. `formatEventMonth` is rewritten to use `Intl.DateTimeFormat(..., { month: "short" })` instead of a hardcoded array.
5. **Relative-time wording mechanism**: approved — keep the existing hand-rolled minute/hour/day threshold logic in `formatRelativeTime`, translating only the unit words via `i18next`'s built-in `_one`/`_other` pluralization; no `Intl.RelativeTimeFormat` introduced (one locale mechanism, not two).
6. **Server error-message localization**: approved — the server stays English-only/locale-unaware in its `error` field (dev/log-facing text), but every error response gains a stable machine-readable `code` field; the client maps `code` → translated string with a generic translated fallback for unrecognized codes, and no screen ever renders a raw server `error` string to the user again. Rejected alternative: making the server `Accept-Language`-aware and returning pre-translated `error` text — this would duplicate translation maintenance across two codebases and contradicts "never trust API error strings as pre-localized display text", a standard i18n practice.
7. **Locale persistence mechanism**: approved — `AsyncStorage` key `"oursport-locale"`, read once on first launch before auto-detection, exactly mirroring the existing `"oursport-theme"`/`"hasSeenOnboarding"` pattern. No server-side persisted locale field.
8. **Where manual language switching is available**: approved — both a lightweight control on `WelcomeScreen` (pre-authentication) and a `Chip`-based "Sprache" row in `ProfileScreen` (post-authentication, directly under "Darstellung"), so the choice isn't gated behind having an account.
9. **Translation quality bar for this slice**: approved — machine/approximate French and English translations are acceptable to ship; a native-speaker review pass is a non-blocking follow-up, not a requirement of this slice's acceptance criteria.
10. **Scope of surfaces translated**: approved — all 14 screens, the 2 components with their own literal copy, and the 3 affected `lib/` modules are translated in this single pass (no further phasing) — per the roadmap brief, partial translation would leave the app visibly broken (mixed-language), so "every surface" is the realistic minimum viable scope here, not gold-plating.

### Genuinely open questions

1. **App store listing localization**: should the Expo/EAS build metadata and the eventual App Store/Play Store listing text (name, description, screenshots) also be localized per store market, or is that handled separately whenever store submission is actually set up? This doc scopes only the in-app runtime experience; store listings are a distinct, later concern with its own submission workflow this team hasn't started yet.
2. **`en`/`fr` regional variant**: is `en-US`/`fr-FR` the right concrete regional tag (vs. `en-GB`/`fr-CH`, given the app's Swiss/`de-CH` origin), or does the product owner have a specific regional-market preference (e.g. the app may primarily target Swiss French/English speakers, where `fr-CH`/`en-GB`-style date conventions might read more naturally)? Decided pragmatically above as `en-US`/`fr-FR` for this slice; flagging in case the target market is specifically Swiss-French/Swiss-English and a different regional tag is preferred.
